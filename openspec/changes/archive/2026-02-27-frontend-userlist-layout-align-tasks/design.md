## Context

当前 `frontend/` 已有 `Tasks` 页面作为 CRUD 布局参考实现，而 `UserList` 页面在结构分层、操作区位置与列表容器组织上未与其保持一致。该差异增加了页面认知成本，也让后续复用通用布局模式变得困难。此次变更仅针对前端页面结构与组件编排，不涉及后端接口、状态管理协议或路由语义变更。

## Goals / Non-Goals

**Goals:**
- 将 `UserList` 页面重构为与 `Tasks` 页面一致的 CRUD 布局骨架。
- 复用现有布局组件与样式约定，避免新增自定义设计语言。
- 保持现有用户列表功能、查询行为和 API 调用不变。
- 为后续同类页面复用统一模板提供可参考实现。

**Non-Goals:**
- 不新增用户管理业务能力（如新筛选器、批量操作、额外弹窗流程）。
- 不修改后端接口、OpenAPI 契约或数据模型。
- 不进行跨页面视觉主题重设计。

## Decisions

1. 对齐现有 `Tasks` 页面信息架构而非新建布局模式。
   - Rationale: 项目中已有可用 CRUD 规范，直接复用可减少设计与实现分歧。
   - Alternative considered: 为 `UserList` 单独设计新布局；否决原因是会继续扩大同类页面差异。

2. 采用“结构重排优先、行为逻辑最小改动”的实施策略。
   - Rationale: 降低回归风险，确保此次迭代聚焦规范化。
   - Alternative considered: 同步重构状态与数据层；否决原因是超出本次变更范围。

3. 以页面可验证的结构约束定义验收标准（标题区、操作区、数据区对齐）。
   - Rationale: 布局类需求需要可测试描述，避免主观解释偏差。
   - Alternative considered: 仅给视觉说明；否决原因是难以形成稳定回归检查。

## Risks / Trade-offs

- [Risk] 页面结构重排可能影响已有交互控件位置与可发现性 → Mitigation: 严格参照 `Tasks` 页面区域顺序，保留原功能入口语义与命名。
- [Risk] 引用组件替换可能引入样式抖动 → Mitigation: 优先复用同源组件与容器类，不新增全局样式 token。
- [Trade-off] 维持逻辑不动会保留部分历史实现细节 → Mitigation: 在本变更先完成布局一致性，后续再按需要做专项清理。

## Migration Plan

1. 识别 `Tasks` 页面布局结构与 `UserList` 现状差异。
2. 在 `UserList` 页面中调整容器层级、页面头部与操作区布局。
3. 验证列表渲染、操作按钮与路由行为与变更前一致。
4. 在本地前端回归后合并变更；若发现问题可通过回滚页面结构改动恢复。
